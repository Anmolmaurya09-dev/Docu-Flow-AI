# Build Docu-Flow AI — A Free, Local-First Developer Tools Web App

Act as a senior frontend engineer, UI/UX designer, and beginner-friendly coding mentor. Build a complete, working web application called **Docu-Flow AI** from scratch.

## 1. Main objective

Create a polished, easy-to-use developer documentation and utility website inspired by the simplicity of iLovePDF. Users should immediately understand what each tool does, select it, enter or upload their information, and get a useful result they can copy or download.

Use iLovePDF only as inspiration for usability and clear tool selection. Do not copy its logo, branding, exact layout, or copyrighted assets.

The priority order is:

1. All core features must genuinely work.
2. The interface must look polished, modern, consistent, and easy to use.
3. The app must be free to run for the owner wherever reasonably possible.
4. The code must be organized and easy for a beginner to maintain manually.
5. Avoid unnecessary features and dependencies.

## 2. Technology and cost restrictions

* Use React, TypeScript, and Vite.
* Build a frontend-only, static web application that can be deployed to a free static hosting plan.
* Process user files and inputs locally in the browser whenever possible.
* Do not create an Express server, database, authentication backend, or server-side API.
* Do not use PostgreSQL, paid AI APIs, paid third-party services, or services requiring a credit card.
* Do not add login, sign-up, user profiles, account settings, subscriptions, payments, premium plans, or billing.
* Do not add API keys, secrets, or environment variables unless absolutely necessary; the initial version should not need any.
* Do not send uploaded files, source code, or user-entered text to an external server.
* Never execute uploaded code. Analyze it only as text.
* Avoid analytics, tracking, advertising integrations, and external API calls in version one.
* Do not claim the app uses AI when a feature actually uses deterministic templates or local parsing.
* Do not introduce a dependency unless it provides a clear benefit.
* Never configure a paid deployment or service that could create unexpected charges.

Before building, briefly state the architecture and any dependencies you plan to use. Then implement the app. If a requested feature requires a paid service, replace it with a local alternative and explain the limitation.

## 3. Design and interface

Create a premium-looking dark interface with a simple, approachable experience.

Visual direction:

* Dark navy or charcoal background.
* White, readable text.
* Cyan/blue accents with restrained purple gradients.
* Rounded cards, subtle borders, consistent spacing, and clean icons.
* A simple lightning-bolt logo and the product name “Docu-Flow” with a small “AI” badge.
* Clear headings, short descriptions, and obvious primary buttons.
* Subtle hover and focus states; avoid excessive animations.
* Responsive layouts for mobile phones, tablets, and desktops.
* Accessible contrast, keyboard navigation, and visible focus indicators.

Homepage:

* Header with logo, tool navigation, and a simple “Free tools” label.
* Hero heading explaining that users can create and organize developer documentation without unnecessary setup.
* Four clearly displayed tool cards.
* Each card must have an icon, name, short description, and working “Open tool” action.
* A clean workspace for the selected tool, with a clear way to return home.
* Helpful empty states, loading indicators only where genuinely needed, success messages, and readable error messages.
* Footer with About, Privacy, and Feedback sections or pages.

Do not add fake buttons, fake statistics, fake testimonials, fake pricing, or features that do not work.

## 4. Four core features

### Feature 1: README Studio

Create a form for generating a useful README.md file.

Include fields for:

* Project name
* Short description
* Problem the project solves
* Main features
* Technologies used
* Installation instructions
* Usage instructions
* Project status
* License
* Author or project links (optional)

Requirements:

* Generate real Markdown from the supplied information.
* Show a live or refreshable preview.
* Include working Copy Markdown and Download README.md buttons.
* Provide a useful sample/template option.
* Allow the user to edit the generated Markdown before copying or downloading.
* Escape or safely render user input; do not execute HTML or Markdown as code.
* Never invent project features, test results, security claims, or installation commands.

### Feature 2: Project Analyzer

Allow users to select a project ZIP file and inspect it locally in their browser.

Use a suitable lightweight ZIP-reading library only if needed. Do not upload the ZIP to a server.

Requirements:

* Read package.json when present.
* Show project name, description, dependencies, development dependencies, and available scripts.
* Display a simplified project file/folder tree.
* Count supported files and estimate lines of code for readable text files.
* Identify common project technologies only when supported by actual files.
* Explain what was detected and what could not be determined.
* Offer a downloadable project summary.
* Handle invalid ZIP files, missing package.json, unsupported files, and large files gracefully.
* Never execute npm scripts, source files, or other uploaded content.
* Skip common bulky folders such as node_modules, dist, build, and .git where possible.
* Do not claim to detect vulnerabilities or perform a real security audit.

### Feature 3: Developer Utilities

Build a collection of genuinely working local utilities within one tool area:

1. JSON validator and formatter, with understandable errors.
2. .gitignore generator with selectable templates for common languages and frameworks.
3. Markdown formatter with sensible basic formatting and no destructive changes.
4. Changelog template generator.
5. Code text statistics, including characters, words, lines, and blank lines.

Each utility must have its own clear inputs, output area, reset action, and copy or download option where relevant.

Use local code and templates. Do not require an API.

### Feature 4: Documentation Pack

Create a tool that combines information entered by the user with real metadata extracted by the Project Analyzer to generate a documentation pack.

Include:

* README.md
* Installation guide
* Getting-started/onboarding guide
* Project structure summary

Requirements:

* Let users enter missing descriptions and setup instructions.
* Reuse actual detected project information when available.
* Clearly label template-generated suggestions and user-provided information.
* Do not invent commands, architecture details, features, or project structure.
* Allow users to preview and edit each document.
* Provide individual downloads and a single ZIP download containing the generated documents.
* If no project ZIP is supplied, allow manual entry and clearly label the output as template-based.
* Process everything locally.

## 5. File and resource limits

Implement reasonable, clearly displayed limits:

* Maximum project ZIP size: 5 MB.
* Maximum files processed per ZIP: 100.
* Skip oversized or unsupported text files gracefully.
* Never extract or execute files onto a server.
* Never make a network request just to process a user's project.
* Allow unlimited normal use of local tools, subject to browser performance and the stated file limits.
* Validate file types and sizes before processing.
* Show understandable errors instead of crashing.
* Avoid retaining uploaded files after the current task finishes. Do not use local storage to save uploaded source code by default.

## 6. Privacy and trust

Create a concise Privacy page explaining that the initial version processes inputs locally in the browser and does not intentionally upload files to a server.

Only make claims that match the implementation. If any dependency sends data externally, disclose it or remove it.

Warn users not to share private keys, passwords, tokens, or confidential code. Do not log their input or source files.

## 7. Code quality and maintainability

* Use a clean, understandable folder structure.
* Keep the four tools in separate components or modules.
* Separate UI components from file parsing, Markdown generation, and utility logic.
* Use clear TypeScript types.
* Avoid giant components and duplicated logic.
* Add short comments to explain non-obvious code.
* Keep dependencies minimal.
* Do not rewrite working code unnecessarily.
* Do not create mock implementations in place of real functionality.
* Ensure the project builds without TypeScript errors.
* Provide a README with installation, development, build, and deployment instructions.
* Include a clear list of files created and explain the main folders in beginner-friendly language.

## 8. Testing and completion

Test the actual workflows, not just the appearance.

At minimum verify:

* Every tool card opens the correct tool.
* README generation, preview, editing, copying, and downloading work.
* Valid and invalid JSON are handled correctly.
* .gitignore templates generate usable output.
* Project ZIP analysis works with a sample project.
* Missing or invalid ZIP files produce helpful errors.
* Documentation Pack generates the expected files and ZIP.
* File-size and file-count limits work.
* Mobile layouts are usable.
* Refreshing the page does not break the application.
* There are no fake success messages or nonfunctional buttons.
* A production build completes successfully.

If you cannot test a workflow, state that honestly instead of claiming it passed.

## 9. Work carefully

First inspect the environment and explain the planned approach. Then implement the complete first version without adding unrelated features.

Do not waste time on login, payments, databases, AI API integration, or a complicated backend. Keep the application local-first and simple enough that I can later ask another assistant to help me manually edit individual files without using the Replit AI Agent.

When finished, give me:

1. A summary of what works.
2. The exact command to run the app.
3. The exact command to build it.
4. Any tests performed and their actual results.
5. The free deployment options and any relevant limitations.
6. Any remaining bugs or incomplete features.

The final result should be a genuinely useful, functional developer utility website, not just a beautiful mockup.

## Mandatory UI Design — Follow This Layout

The dark Docu-Flow interface shown in the design reference is my preferred design. Reproduce its overall layout and visual style as closely as possible.

* Dark navy background with white text, cyan highlights, and subtle purple accents.
* Header with the lightning-bolt icon, “Docu-Flow” branding, a small “AI” badge, and a “Free tools” label.
* Large hero heading: “Everything your project needs.”
* Short supporting description about documentation and developer utilities.
* A wide search bar labeled “Search developer tools...”
* A “Documentation” heading followed by four cards in a two-column desktop grid:

  1. README Studio
  2. Project Analyzer
  3. Developer Utilities
  4. Documentation Pack
* Each card must have a suitable icon, clear title, short description, rounded dark surface, subtle border, and consistent spacing.
* Under the main cards, include a “Quick tools” section with compact shortcuts such as JSON Formatter, Text Diff, Markdown Preview, and .gitignore Generator.
* Use the same visual language on every tool page, including inputs, dropdowns, previews, buttons, and error messages.
* On mobile, make the layout responsive and stack the cards appropriately.
* Do not replace this layout with a generic dashboard, a sidebar-heavy admin panel, a white template, or a completely different design.
* Keep the interface uncluttered and easy for first-time visitors.
* Make the search bar, cards, and shortcuts functional. Search should filter available tools, and selecting a card should open the corresponding tool.
* Include a subtle future-ready place for Premium labels, but do not add login, subscriptions, payment processing, or nonfunctional Premium buttons.
* Do not sacrifice working functionality for visual effects.

Treat this UI specification as a requirement, not an optional suggestion. Before finishing, compare the implemented homepage against every bullet above and correct any missing elements.
